# 成员三：预订模块

你只改 `bookings/`。测试数据已包含 student1 的物品、买家 student2/student3 及一条 ACTIVE；不用等成员二做发布。

## 要完成的功能

1. 实现 services.reserve：不能预订自己物品；AVAILABLE 才能成功；ACTIVE 占用唯一；使用 request_key 幂等，同一买家同 key 重试返回原预订，同 key 换物品返回 409。
2. 我的预订：只显示当前买家记录，含物品、状态、到期时间；可取消自己的有效预订。取消后物品 AVAILABLE，重复取消无新增副作用。
3. 双方确认：买卖双方各一次，第二方才将两表状态设 COMPLETED；同一侧重复不能算双确认。非交易方 403，过期/取消/作废不能确认，完成后相同参与者重试返回原结果。
4. 到期：时长取 settings 配置；now ≥ expires_at 就释放。实现 expire_due 和现有 expire_reservations 命令；再加 run_expiry_worker 命令，每 60 秒回收，支持 Ctrl+C 退出。单次任务可重复执行。
5. 实现预订按钮、买家中心和卖家确认按钮。脚本通过 fetch + FormData + CSRF 调现有 POST 入口，展示成功/冲突信息；按钮禁用仅作体验，后端仍验证。

## 关键规则

统一用 core 的模型、Result、lock_listing、release_if_expired；所有状态更改先锁 Listing，再锁 Reservation。业务失败正常返回 Result，让已做的到期释放提交，不要抛业务异常把释放回滚。初步授权失败不能释放他人的预订；锁内还要复核。

预订、取消、确认都要处理到期；worker 停止时，新的预订仍可释放旧占用后成功。`reserve` 锁内再次检查幂等 key，终态原记录不得复活；数据库唯一约束失败要先回滚再处理，不能在失败事务里继续查询。每个物品单独短事务。

同侧确认不延时。仅有一方确认时买家仍可在有效期内取消。状态组合见公共约定，不能为方便演示跳过规则。鉴权按当前用户判断买/卖，不从 body 接收角色。

## 怎么算做完

测试至少覆盖：成功、自买、非可用状态、重复 key、跨物品 key、取消与终态、双侧/单侧重复确认、第三方操作、精确到期边界、任务延迟、管理员隐藏后的 VOID。

真正并发测试用 PostgreSQL 不同连接、同步起跑：100 个买家抢一件物品，10 轮，每轮恰好一个有效预订；同时验证取消/确认、到期/确认的合法结果。SQLite 测试通过不能声称已验证抢单并发。

在 bookings/开发记录.md 写操作步骤、启动 worker 方法、实际测试结果和未验证项。只提交 bookings/，发 PR 到 main。
