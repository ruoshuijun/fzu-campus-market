# 成员四：你现在怎么做

## 已替你完成

- 公共 Django 项目、三个业务模型和迁移、统一网址与状态规则。
- 演示账号与数据，基础登录、物品浏览、模块入口和公共样式。
- 你的管理员模块 moderation：管理台、隐藏原因、同步结束预订、操作记录。
- 事务锁工具、基础测试、PostgreSQL 可选配置和 GitHub CI。
- 三位同学各自的任务书与预留接口。

成员一至三的完整业务仍由他们开发。当前底座可以运行，但尚不能完成新预订；不要把占位页当完整项目交作业。

## 第一步：把同一份底座发给三个人

已有 GitHub 仓库时，直接从邀请三位协作者开始。需要从 ZIP 副本创建仓库时，先在 GitHub 建空仓库 `fzu-campus-market`，再在项目目录执行以下命令，把 `OWNER` 换成你的账号。

```powershell
git init -b main
git add .
git commit -m "chore: add shared Django foundation"
git remote add origin https://github.com/OWNER/fzu-campus-market.git
git push -u origin main
```

1. 邀请三人为协作者。他们各自 clone **整个仓库**，读对应任务书，把最后一段复制给 AI。
2. 各自创建 `feat/accounts`、`feat/items`、`feat/bookings` 分支，只改自己的目录。

## 第二步：你在他们开发时做什么

- 用 admin 登录管理台检查隐藏和审计；普通账号访问必须拒绝。
- 接受必要的公共字段/接口变更，统一修改 core 与迁移并通知所有人同步 main。
- 有 Docker 时启动 PostgreSQL，照 README 执行测试；没有时先用 SQLite 跑页面，最终并发必须在 PostgreSQL 验证。
- 不用再另写聊天、支付或推荐功能。每人先把一小段功能 PR 过来，你在中途先合并一次检查，不等最后一天。

## 第三步：依次整合

账号 PR → 物品 PR → 预订 PR。因为目录分开，通常可以直接合并；公共文件冲突由你逐项确认，不让 AI 用整份文件覆盖。

每次合并后运行：

```powershell
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py test
```

检查网页：学生注册/登录 → 发布物品 → 另一学生搜索 → 预订 → 取消再预订 → 双方确认。再测超时、两个买家抢一件物品、管理员隐藏已预订物品。失败就把最小复现发回对应负责人，不在最后自己重写三个人的模块。

GitHub CI 是上传后自动运行的；首次云端通过后，能使用分支保护的仓库再要求 CI 和至少一人批准。最终打 v1.0 标签，保留录屏和课程过程证据。

## 直接复制给 AI（整合时）

> 我是成员四。请先读 AGENTS.md、docs/公共约定.md 和 docs/成员4-整合.md。检查其他三个成员分支或已合并代码，按固定模型、路由和 Result 契约逐一整合。先给出实际冲突位置，再做必要修复；不要把其他人的模块整体重写或覆盖。运行迁移检查和全量测试，走通完整业务流程。检查管理员隐藏与预订一致性、权限和 PostgreSQL 并发测试；未执行项目明确报告。最后更新 README 的实际启动步骤，保留各人的贡献。
